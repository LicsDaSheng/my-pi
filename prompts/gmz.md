# gmz - 中文 Git 提交

读取当前仓库中所有已暂存（staged）的改动，分析变更内容，然后根据当前工作目录采用对应的中文提交规范并执行提交。

## 提交规范分流

执行提交前，先使用 `git rev-parse --show-toplevel` 确认当前 Git 工作树根目录：

- **当工作树根目录为 `~/work` 时**：采用「个人工作日志」式提交信息，清晰记录当前完成了什么，方便后续按提交历史回看工作。不要使用 `feat`、`fix`、`docs` 等代码开发式 Conventional Commits 类型。
- **编程项目目录**：继续采用本提示词原有的 Conventional Commits 中文提交规范。

## 工作流程

1. 执行 `git status` 和 `git diff --staged` 查看所有暂存内容，同时检查是否存在未暂存（modified / untracked）的改动
2. 如果没有任何暂存内容，直接告知用户"没有已暂存的改动"，不要执行提交；同时告知用户有哪些未暂存的改动，询问是否需要一并暂存并提交
3. 判断当前 Git 工作树根目录，并按「提交规范分流」选择提交信息风格
4. 分析变更的性质、范围以及本次实际完成的工作
5. **如果存在未暂存的改动，必须先与用户确认**：列出这些文件，询问是否需要一并 `git add` 后再提交。得到用户明确答复前，不要擅自添加未暂存的文件，也不要直接执行提交（除非用户明确表示只提交暂存区内容）
6. 用中文撰写符合当前目录规则的提交信息
7. 执行 `git commit` 完成提交

## `~/work` 提交信息格式

提交信息按个人工作日志组织：

```text
<中文标题：概括本次整理或完成的工作>

本次完成并记录了以下工作：

- <完成事项 1>
- <完成事项 2>
- <必要时记录状态同步、结论或后续回看线索>
```

示例：

```text
整理 W36 工作进展与周报思考

本周完成并记录了以下工作：

- 汇总 TCL 方案、机械臂统一接入方案和 phys-agent 收尾进展
- 核对 Cosmos 初步调研成果，同步更新 OKR、待办和工作日志
- 完成 W36 周报，补充 Agent 适配个人工作方式的思考
```

要求：

- 标题和正文均使用简体中文
- 标题直接说明“当前做了什么”，避免抽象表述
- 正文根据实际变更列出已完成事项，便于以后通过 Git 历史还原工作过程
- 使用个人工作记录的视角，不使用 `feat:`、`fix:`、`docs:` 等代码开发式前缀
- 不夸大完成状态；进行中、等待依赖、仅形成初稿等情况应如实描述

## 编程项目目录的提交类型

- `feat`: 新功能
- `fix`: 修复 bug
- `docs`: 文档变更
- `style`: 代码格式调整（不影响功能）
- `refactor`: 重构（非新功能、非修复）
- `perf`: 性能优化
- `test`: 测试相关
- `chore`: 构建、依赖、配置等杂项
- `ci`: CI/CD 变更

## 编程项目目录的提交信息格式

```
<type>: <中文描述>
```

示例：
- `feat: 新增用户登录接口`
- `fix: 修复列表分页越界问题`
- `docs: 更新 README 安装说明`

要求：
- 描述使用简体中文，简洁准确，概括本次变更的核心内容
- type 保持英文小写，冒号后有一个空格
- 如果变更涉及多个方面，选取最主要的一个类型，描述中概括要点；必要时可在正文部分用列表补充细节
- 未经用户确认，**不要**执行 `git add` 添加未暂存的文件
