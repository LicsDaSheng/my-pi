# 测试驱动开发（TDD）

以可观察的行为为中心完成代码改动。先用测试说明期望，再写刚好让测试通过的实现；每次重构后都保持相关测试通过。

## 开始前

1. 阅读项目的 `AGENTS.md`、测试配置和已有的相邻测试，采用项目已有的语言、框架、断言风格及测试命令。
2. 将需求归纳为用户旅程或可验证的行为，并列出正常路径、边界条件和失败路径。
3. 按风险选择测试层级：纯逻辑优先单元测试；跨模块、数据库、网络或 API 契约使用集成测试；关键用户流程才使用端到端测试。不要为凑覆盖率而重复测试同一行为。

## Red → Green → Refactor

### Red：先写失败测试

- 每个测试只描述一个行为，采用清晰的 Arrange–Act–Assert 结构和行为导向的名称。
- 测试公开行为、返回值、状态转换或用户可见结果；避免耦合私有实现、内部状态和脆弱的样式选择器。
- 测试应相互隔离：自行准备数据与依赖、清理副作用，不依赖执行顺序或外部共享状态。
- 执行最小相关测试，确认它因尚未实现的行为而失败，而不是因语法、环境或旧回归失败。

### Green：最小实现

- 仅实现让当前测试通过所需的行为；不要在没有测试约束时顺带扩展范围。
- 外部服务、时钟、随机数和 I/O 应在合适层级替换或隔离，避免真实网络调用和不稳定测试。
- 重新执行相关测试；若失败，先修正实现或测试假设，再继续下一个行为。

### Refactor：保持绿色地改进

- 在测试保护下消除重复、改善命名和结构；必要时补充覆盖新分支的测试。
- 完成后运行与改动范围相称的测试套件，以及项目已有的 lint、类型检查或构建检查。

## 覆盖与完成条件

- 覆盖所有新增或变更行为的成功、边界和错误情形；异常输入、空值、权限、超时与降级路径按实际风险选择。
- 若仓库定义了覆盖率阈值，遵守并运行其覆盖率命令；若没有，不臆造统一的百分比或强制要求每次改动都写 E2E 测试。
- 不提交跳过、禁用或为了通过而弱化的测试，除非用户明确接受并记录原因。
- 交付时说明运行过的验证及结果；无法运行的检查要说明原因和未验证范围。

## 常见判断

| 情况 | 做法 |
| --- | --- |
| 修复回归缺陷 | 先写能复现缺陷的测试，再修复。 |
| 重构 | 先为现有关键行为建立保护测试；重构期间持续运行它们。 |
| API 或存储交互 | 为契约、验证、错误映射和持久化结果写集成测试。 |
| 浏览器界面 | 以语义角色、可访问名称或稳定的 `data-testid` 定位；仅为关键旅程写 E2E。 |
| 测试无法先写 | 说明阻碍，先创建最小可执行的行为规格或测试支架；不要把“无法先写”作为直接跳过验证的理由。 |

## 不要做

- 把覆盖率数字当作质量的唯一证明。
- 测试私有变量、精确 DOM 结构、生成的 CSS 类名等实现细节。
- 让测试依赖真实第三方服务、当前时间、随机结果或其他测试的残留状态。
- 在未检查失败原因的情况下，把 Red 阶段的红灯当作成功。
